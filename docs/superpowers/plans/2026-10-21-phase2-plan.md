## 3. M1a: files between v0.4 apps

**Goal:** a director on the new app sends a batch of files to one or more v0.4 actors over `/v2/ws`, with character
routing, a prompt or auto-accept on the actor, SHA-256 checks, atomic writes, progress, and Cancel that works mid-file.

### 3.1 Messages (new models in `protocol/vrcas_protocol/messages.py`)

All replies go to `{ids: [<sender of the offer>]}`. `transfer_id` is 32 hex characters (the 16-byte UUID in the binary
frames).

| Type | From | `data` |
|---|---|---|
| `file.batch.start` | director | `batch_id`, `files`, `bytes` |
| `file.offer` | director | `transfer_id`, `batch_id?`, `name` (base name), `size` (≤ 1 GiB), `chunk_size` (16–256 KiB, default 256 KiB), `sha256?`, `md5?`, `character?`; at least one hash. Must target exactly one session |
| `file.accept` | actor, camera | `transfer_id` |
| `file.deny` | actor, camera | `transfer_id`, `reason` |
| `file.progress` | actor, camera | `transfer_id`, `received` (chunks so far) |
| `file.end` | director | `transfer_id`, `sha256?`, `md5?` |
| `file.ok` | actor, camera | `transfer_id`, `saved_as` (shown to the director) |
| `file.err` | actor, camera, relay | `transfer_id`, `error` |
| `file.batch.end` | director | `batch_id`, `ok`, `failed` |
| `file.batch.cancel` | director | `batch_id`, `reason` |

- `md5` is there for v0.3 actors (M1b: their `FILEEND` carries MD5). The director's agent computes both in one pass.
- `chunk_size` is declared per offer rather than fixed at 256 KiB, so the bridge can pass a v0.3 director's 64 KiB
  chunks through without re-chunking (§20.1 note).
- **Binary frames** (§5.7): `vrcas_protocol/chunks.py` with `pack(kind, transfer_id, index, payload)` / `unpack(frame)`;
  kind `0x01` = file chunk; header 21 bytes; payload ≤ the offer's `chunk_size`.
- **Flow control:** at most 8 chunks in flight; `file.progress` after each chunk written.
- **Cancel:** `file.batch.cancel` at any time. The director stops sending; the actor deletes the current partial file
  and drops prompts from that batch. Every send from the new app is a batch, even one file.

### 3.2 Permission rows

None to add: `server/permissions.py` already has `file.offer`, `file.end`, `file.batch.*` (director) and
`file.accept/deny/ok/err/progress` (actor, camera). Binary chunk frames are checked as `file.offer` (director only).
`tests/test_permissions.py` must still pass unchanged.

### 3.3 Relay (`server/`)

- New `server/transfers.py`: `Transfer(id, batch_id, sender, recipient, size, chunk_size, accepted, received)`.
  - `file.offer` routed to one session registers a transfer (an offer to several ids or a role → `error invalid`).
  - `file.accept` from that recipient marks it accepted.
  - A binary frame: unknown transfer → `error invalid`; sender isn't the transfer's sender → `forbidden`; not accepted
    yet → `invalid`; index past the end → `invalid`; else forwarded to the recipient as is (`Session.send_bytes`, new).
  - Removed on `file.ok` / `file.err` / `file.deny`, on `file.batch.cancel` (all transfers of that batch), and when
    either side disconnects: the other side gets `file.err {transfer_id, error: "<name> disconnected"}` from the relay.
  - Limits in `Settings`: binary frame ≤ 21 B + 256 KiB, offer `size` ≤ 1 GiB, ≤ 16 open transfers per sender.
- `router.py`: `_receive` accepts binary frames (today `error unsupported`) and hands them to `transfers`; `route()`
  updates the table for `file.*` types.
- Bridge (M1a only): a v0.3 director's `FILEREQ` to a v2 actor is still declined with a reason, unchanged.
- D5 (if yes): one `server.log` line when a transfer ends: `File Mira → Coda: Scene 4 - Diego.mp3 (1.2 MB): ok`.

**What changes for connected clients at the next live restart (M1a):**
- v0.3 clients: nothing. `/ws` code isn't touched; the golden transcript passes.
- v2 clients: binary frames are accepted from directors (only for accepted transfers) instead of answered with
  `error unsupported`. `file.*` messages are validated: a malformed one gets `error invalid` instead of being routed.
  No released build sends either. Older v0.4 actor builds (no `files` capability) are never offered files by the new
  director UI.

### 3.4 Agent

- New `agent/files.py`:
  - `Receiver` (actor and camera): policy (receive folder, auto-accept), prompt queue for the UI, writes to
    `<folder>/.<name>.<id8>.part` at `index × chunk_size`, verifies SHA-256 (or MD5 when that's all the offer has),
    `os.replace` into place, `file.ok` / `file.err`. Refuses before accepting: unsafe names (path separators, `..`,
    control characters, Windows device names like `CON`/`NUL`/`COM1`, trailing dots/spaces, > 200 characters), files
    over 1 GiB, not enough free disk space. Appends `{sha256, path, name, from, at}` to `<data dir>/received.json`
    (M2 uses it for `{sha256}` sound references and auto-add).
  - `Sender` (director): batches, one file at a time per actor, actors in parallel; hashes in a thread; reads 256 KiB
    at a time; ≤ 8 chunks in flight; Cancel per batch and Cancel all; a stall timeout of 60 s once sending (no
    `file.progress`) ends the batch (built that way: an actor that stopped answering would fail the rest too). No
    timeout while an offer waits for the actor's answer (v0.3 had none either); Cancel ends it.
- `agent/folders.py`: a send listing (all regular files if D2 = any type, hidden files and `.part` files skipped). Reads
  stay limited to folders opened in this run.
- `agent/relay_v2.py`: routes `file.*` and binary frames to `files.py`; actors announce capability `files`.
- `agent/config.py`: `files: {receive_dir, auto_accept}`; v0.3 import of `receive_dir` and `auto_accept_files`.
- Compatibility mode (v0.3.3 relay): no file transfer, as now (actors decline `FILEREQ` with a reason).

## 4. M1b: files between v0.3 and v0.4 (bridge)

**Goal:** a v0.3.3 director sends to a v0.4 actor, and a v0.4 director sends to a v0.3.3 actor, with batches and
cancel. Spec §11.2: "the bridge converts base64 ⇄ binary and 64 KB ⇄ 256 KiB chunks".

**This changes what v0.3 clients receive, so I wait for your OK on this list before writing it.**

### 4.1 What v0.3 clients will see (exact frames)

**A. v0.3.3 director → v0.4 actor** (an actor whose app announces `files`):

| Today | After M1b |
|---|---|
| `FILEDENY\|<name>\|<actor> uses vrcActorSync 0.4, which can't receive files from a v0.3 director yet` | The normal v0.3 replies, as from a v0.3 actor: `FILEACK\|<name>\|1\|` (empty save_dir), then `FILEOK\|<name>\|<saved_as>`, or `FILEDENY\|<name>\|<reason>`, or `FILEERR\|<name>\|<error>` |
| `BATCH_START` / `BATCH_END` / `BATCH_CANCEL` to a v0.4 actor dropped | Passed on as `file.batch.*` (the director sees nothing different) |

- An older v0.4 actor without `files` still gets today's `FILEDENY`, with the reason "…uses an older vrcActorSync 0.4
  preview; update it to receive files".
- Translation: `FILEREQ` → `file.offer` (`md5` = its checksum, `chunk_size` 65536); `FILESTART` swallowed;
  `FILECHUNK` → one binary frame (index = chunk_num); `FILEEND` → `file.end {md5}`. The v0.4 actor's `file.progress`
  isn't passed back (v0.3 has no equivalent).
- `saved_as` is what the v0.4 actor reports: its receive-folder name and the file name (e.g.
  `vrcActorSync\Scene 4 - Diego.mp3`), not a full path.

**B. v0.4 director → v0.3.3 actor:** the same frames a v0.3.3 director sends, in the same order:

```
BATCH_START|<actor name>|<files>|<bytes>          (left out for a batch of one file, D12)
FILEREQ|<director name>|<actor name>|<name>|<size>|<md5>
  … actor answers FILEACK or FILEDENY …
FILESTART|<name>|<ceil(size / 65536)>|65536
FILECHUNK|<name>|<n>|<base64 of 64 KiB>          (4 per 256 KiB binary chunk, n counts from 0)
FILEEND|<name>|<md5>
  … actor answers FILEOK / FILEERR / FILEDENY (declined overwrite) …
BATCH_END|<actor name>|<ok>|<failed>
BATCH_CANCEL|<actor name>|<reason>                 (on Cancel; no more FILECHUNK or FILEEND for that file)
```

- Differences from a v0.3.3 director: `FILEREQ` names the real director instead of the hard-coded `Director`; a
  mid-file Cancel stops the chunks, so the v0.3 actor never gets `FILEEND` and writes nothing.
- The bridge paces the v0.4 director: it sends `file.progress` after the 4 frames of a chunk have gone out.
- `FILEEND` carries the director's MD5 from the offer, so the v0.3 actor checks the whole path end to end.
- Names with `|`, `/`, `\`, control characters or `..` are refused with `file.err` (a v0.3 actor joins the name
  onto its folder unchecked). The new director's sanitizing already prevents them.
- A second offer of the same file name to the same v0.3 actor while one is open → `file.err "busy"` (v0.3 keys
  transfers by file name, §17 #4).
- v0.3 ↔ v0.3 transfers keep using today's table and code path; the golden transcript is unchanged.
